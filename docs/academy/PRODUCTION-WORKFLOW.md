# Academy production workflow

The Academy backlog is now an executable dependency graph. [`BACKLOG.md`](BACKLOG.md) remains the sole completion authority; this workflow schedules it without creating a second product truth.

## Commands

```bash
node scripts/academy-production-workflow.mjs validate
node scripts/academy-production-workflow.mjs status
node scripts/academy-production-workflow.mjs ledger
node scripts/academy-production-workflow.mjs plan
node scripts/academy-production-workflow.mjs index-unreachable
node scripts/academy-production-workflow.mjs index-transcripts
node scripts/academy-production-workflow.mjs prune-state
node scripts/academy-production-workflow.mjs salvage GOV-001
node scripts/academy-production-workflow.mjs claim GOV-001 --owner codex-main --paths config/academy-production-workflow.json,scripts/academy-production-workflow.mjs
node scripts/academy-production-workflow.mjs attach-evidence GOV-001 C artifacts/evidence/canonical.json
node scripts/academy-production-workflow.mjs run-proof GOV-001 T -- node node_modules/vitest/vitest.mjs run tests/academy/example.test.ts
node scripts/academy-production-workflow.mjs attest-reuse GOV-001 @workflow-state/reuse/GOV-001.json
node scripts/academy-production-workflow.mjs run-review GOV-001 --provider claude-fable --prompt artifacts/reviews/GOV-001-prompt.md
node scripts/academy-production-workflow.mjs attest-approval GOV-001 owner @workflow-state/evidence/GOV-001-owner-approval.json
node scripts/academy-production-workflow.mjs seal-proof GOV-001 --summary "One verified governance slice"
node scripts/academy-production-workflow.mjs verify-proof GOV-001
node scripts/academy-production-workflow.mjs promote GOV-001 --apply
node scripts/academy-production-workflow.mjs reopen GOV-001 --token CLAIM_TOKEN
node scripts/academy-production-workflow.mjs checkpoint --token CLAIM_TOKEN --message "chore(academy): promote GOV-001"
node scripts/academy-production-workflow.mjs verify-checkpoint --token CLAIM_TOKEN
node scripts/academy-production-workflow.mjs record-release --tag vX.Y.Z
node scripts/academy-production-workflow.mjs recovery-status
node scripts/academy-production-workflow.mjs recover [--rollback|--roll-forward]
```

`ledger` generates `@workflow-state/production-ledger.json`. It is the sole machine-readable delivery view: one row per canonical task records audit, implementation, learner reachability, QA and deployment evidence, while its progress percentages are derived from those same rows. A checked backlog box is reported as `backlogChecked` but counts as `canonicalComplete` only after the exact claim has passed post-push verification and the current task definition, pinned proof, checkpoint commit, and freshly recomputed nested-evidence manifest all agree. A user-visible task additionally requires a successful `record-release`; `awaiting-release` remains open, incomplete and not deployed. The scheduler uses the same state-aware rule, so pending verification/release does not unblock dependants, and a promoted pending task is not offered for a duplicate claim. Draft, interrupted, expired, replaced, cross-task, stale-definition, awaiting-verification, failed-verification and merely self-labelled proof files cannot inflate completion or evidence totals. Route counters are generated from named source registries and carry an explicit claim type so an authored file count cannot be presented as learner reachability. `status` reads this generated ledger rather than calculating a second percentage.

`plan` compiles the canonical checkboxes, dependencies, proof gates, priorities, active claims, lane capacity, and downstream unlock count. It writes resumable work orders, claims, locks, reuse indexes and proof templates beneath the repository's shared Git common directory. Every worktree therefore sees one scheduler state. `YOMU_ACADEMY_WORKFLOW_STATE` can override that location for a controlled CI or recovery run.

## Operating rules

1. Work begins only when every canonical dependency is complete.
2. Before authoring, run the slower `index-unreachable` and `index-transcripts` audits, then `salvage TASK`. The task scan inventories every configured recovery document, path-bearing reachable and unreachable commit, branch, surviving worktree (including tracked and untracked changes), stash, reflog entry, and transcript file from the explicit Claude/Codex roots. Transcript discovery is exhaustive by file path; files with the same basename in different roots retain distinct stable identities. Searchable transcript text is a bounded first/last lexical sample so the index stays small. Candidate ranking ignores generic stopwords, privileges exact task IDs, domain terms and lane-owned paths, and uses `git cherry` to retain patch-equivalent commits in the hashed inventory without proposing duplicate reuse. Every relevant candidate is present in the report and must be explicitly reused or rejected with a reason. Display limits bound only the suggested review queue; omitted display rows remain in the candidate manifest and disposition denominator. Each regeneration records per-source counts, the inventory hash, the source-snapshot hash and a census hash. Counts are observations, not constants. The isolated `GOV-001` snapshot generated at `2026-07-20T08:41:50.056Z` contains 17,196 source rows and census SHA-256 `44be94ca58e4953460fe764d761e1f54018488fb728caf679cb2984de9e3fa21`. Its 2,424 unreachable commits produced 70 relevant dangling-commit candidates under the current task query. An earlier un-hashed “67” cannot identify which three records changed and is not retained as an attested baseline. The regenerated inventory and census hashes, rather than either number, are the comparison authority. Regenerated reports carry forward dispositions only when that stable candidate and its evidence hash still match. A claim pins the content-addressed source snapshot and current recovery-index hashes, rather than livelocking on unrelated worktree edits or an actively growing transcript.
3. Code work uses a clean dedicated worktree starting exactly at current `origin/main`. A claim has a random token, fixed worktree, base commit, expiry, renewal and cancellation path. It must reserve its exact planned files up front; changed files outside that reservation cannot pass proof. Reservation identity is physical: the repository and nearest existing parent are resolved with `realpath`, existing and prospective symlink aliases collapse to one key, and any path that resolves outside the repository is rejected. Every work order carries the lane boundary and the external Japanese/Soya roots when relevant.
4. Parallelism is bounded globally and per lane. Shared state and PID-aware locks live in the Git common directory, while physical file reservations prevent parallel lanes from touching the same file through aliases. Integration remains single-filed.
5. An agent response never closes work. Gate evidence must be a `yomu-academy.gate-attestation/v1` JSON document naming the task, gate, exact HEAD, passing verdict, task owner or allowlisted workflow/CI producer, summary, and hash-bound assertion artifacts. Test commands must be executed by `run-proof`, which records their exit code, transcript and exact Git HEAD. Independent review runs through `run-review`; Node launches the version- and SHA-256-pinned Claude Code binary with a fixed official `claude-fable-5` model, bare/safe mode, no settings sources, no session persistence, an empty strict MCP configuration, disabled slash commands and Chrome, allowlisted read-only tools, and a minimal environment that strips ambient provider/base-URL, cloud, plugin, hook, MCP and settings variables. An explicit `ANTHROPIC_API_KEY` is required because loading a stored CLI login would reintroduce the prohibited user settings boundary; without it the review fails closed. Every recorded identity field comes from the native JSON result: exactly one `modelUsage` key equal to `claude-fable-5`, plus the session ID and result UUID. Those fields are bound to the prompt, response, task definition and HEAD and registered in private shared workflow state before a `ship` attestation can attach. Claude Code does not cryptographically attest which remote service answered, so service/provider provenance remains explicitly `unresolved`; the workflow claims only a verified pinned invocation and native model-output shape. `YOMU_CLAUDE_BIN`, arbitrary provider/model labels, user-authored session files, opaque files, or a review that says `BLOCK` cannot pass.
6. An `owner` requirement accepts only a `yomu-academy.owner-approval/v2` detached Ed25519 signature whose public key and owner ID are pinned in configuration. The canonical signed payload binds schema, task ID and definition hash, requirement, owner ID, purpose, decision, claim token, HEAD, pre-promotion backlog hash, issue/expiry times, a strong one-use nonce and a hash-bound owner-evidence file. The workflow stores only public keys, signatures and nonce registrations; it never generates, requests or stores an owner private key, and fails closed on forgery, replay, expiry, wrong task/purpose/evidence/key or an unregistered nonce. The owner signs through a separate trusted process. This prevents an agent without the private key from fabricating approval, but it cannot defeat a malicious process with the same host/user privileges that can steal or invoke that key; agents sharing that trust boundary are not cryptographically isolated.
7. `seal-proof` only operates on a committed, clean slice. It binds the proof to the current task definition, so another task's checkbox may advance without invalidating parallel work. `verify-proof` fetches `origin/main`, checks claim token/worktree/base/HEAD, verifies the exact committed diff against lane ownership, resolves every evidence path physically (rejecting symlink escapes), opens and hashes every evidence file and nested assertion artifact, and rejects stale or fabricated proof. The reuse attestation must be the exact report pinned when the claim was created.
8. `promote --apply` is the only command that checks a canonical item. Canonical state, backlog and production-ledger transitions use one durable atomic-write module: a fsynced prepared journal records complete before/after images, each target is written by fsync-and-rename, directories are fsynced, and the journal is removed only after completion. Crash injection exists before/after intent, every target write and completion. On restart, untouched transitions roll back and partially applied transitions roll forward. `recovery-status` remains available even when a file transition or legacy prepared promotion is ambiguous; `recover --rollback` and `recover --roll-forward` provide explicit, evidence-preserving choices without hand-editing private state. Promotion and `reopen` update state and backlog in one prepared transition, and ledger regeneration uses the same protocol. Dynamic release scope is resolved to concrete tasks; it no longer leaves `REL-001` permanently unschedulable.
9. The integration lock permits exactly one promoted slice per checkpoint. `checkpoint --token` must name the exact promoted claim and rejects expired or superseded claims. It re-hashes the proof, task definition, expected backlog and every nested review/gate/transcript/assertion/approval artifact before gates, after gates, in a prepared retry commit, and before push, so no extra checkbox, mutated proof, stale task or changed nested evidence can ride along. It refuses an advanced `origin/main` instead of rebasing certified commits, runs configured gates before creating the promotion commit, pushes, confirms `origin/main`, and then enters `awaiting-verification`. Post-push commands must report successful completed checks for that exact commit; every attempt and command transcript is hash-bound under workflow state. Failure moves the claim and promotion to `failed-verification`, leaves completion open, preserves evidence, and supports `verify-checkpoint --token` retry. Non-user-visible work becomes `verified` only after these checks pass. If the base advances or a pre-push gate fails, `reopen` atomically restores the task checkbox and cancels the stale-base claim. The owner then rebases, refreshes salvage, claims again, and reruns gates/review before resealing. User-visible slices move only to `awaiting-release` after post-push success and remain open, incomplete and not deployed until `record-release` verifies the latest non-draft GitHub release, the exact `yomu.user.js` bytes from the tag, the matching changelog entry, and a successful Pages deployment for that tag commit. Only then are the promotion and exact claim `released`. The stability/release lane owns the root version, changelog and built userscript files needed to create that release tree.
10. Failed or interrupted work keeps its local claim/proof state and can resume without redoing completed evidence. Expired claims are excluded from status and return to the scheduler after twelve hours; an expired owner cannot renew over a replacement claim. Command evidence has a bounded output size, and `plan`/`prune-state` remove source snapshots no longer referenced by selected or active work, preventing recovery scans from quietly consuming the disk. Test totals are taken from the current runner output; the former static “41 tests” wording is obsolete because lifecycle coverage changes with the contract.

## Why this shape

The critical path is not “generate more files.” It is: establish authoritative denominators and shared contracts, implement dependency-ready vertical slices, verify them in the real product, integrate one slice at a time, and release continuously. The scheduler therefore rewards P0 work, current focus, and tasks that unblock the most descendants while preventing several agents from editing the same lane at once.

Scheduling, salvage, proof commands and ledger generation remain deterministic and model-independent. The one deliberate exception is `run-review`, where Node launches the fixed Claude Fable policy so the invocation and native output identity can be verified rather than accepted from editable labels. This is not an attestation of Anthropic service provenance.
