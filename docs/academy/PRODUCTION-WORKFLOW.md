# Academy production workflow

The Academy backlog is an executable dependency graph and the canonical task list. Its checkboxes are intent, not sufficient completion evidence: production status is derived from the checked task plus its exact proof, checkpoint on canonical `origin/main`, and release/deployment evidence when applicable.

## Commands

```bash
node scripts/academy-production-workflow.mjs validate
node scripts/academy-production-workflow.mjs status
node scripts/academy-production-workflow.mjs ledger
node scripts/academy-production-workflow.mjs plan
node scripts/academy-production-workflow.mjs index-unreachable
node scripts/academy-production-workflow.mjs index-transcripts
node scripts/academy-production-workflow.mjs prune-state
node scripts/academy-production-workflow.mjs salvage GOV-001
node scripts/academy-production-workflow.mjs claim GOV-001 --owner codex-main --paths config/academy-production-workflow.json,scripts/academy-production-workflow.mjs
node scripts/academy-production-workflow.mjs attach-evidence GOV-001 C artifacts/evidence/canonical.json
node scripts/academy-production-workflow.mjs run-proof GOV-001 T -- node node_modules/vitest/vitest.mjs run tests/academy/example.test.ts
node scripts/academy-production-workflow.mjs attest-reuse GOV-001 @workflow-state/reuse/GOV-001.json
node scripts/academy-production-workflow.mjs run-review GOV-001 --provider claude-fable --prompt artifacts/reviews/GOV-001-prompt.md
node scripts/academy-production-workflow.mjs attest-approval GOV-001 owner @workflow-state/evidence/GOV-001-owner-approval.json
node scripts/academy-production-workflow.mjs seal-proof GOV-001 --summary "One verified governance slice"
node scripts/academy-production-workflow.mjs verify-proof GOV-001
node scripts/academy-production-workflow.mjs promote GOV-001 --apply
node scripts/academy-production-workflow.mjs reopen GOV-001 --token CLAIM_TOKEN
node scripts/academy-production-workflow.mjs checkpoint --token CLAIM_TOKEN --message "chore(academy): promote GOV-001"
node scripts/academy-production-workflow.mjs verify-checkpoint --token CLAIM_TOKEN
node scripts/academy-production-workflow.mjs record-release --tag vX.Y.Z
node scripts/academy-production-workflow.mjs recovery-status
node scripts/academy-production-workflow.mjs recover [--rollback|--roll-forward]
```

`ledger` generates `@workflow-state/production-ledger.json`. It is the sole machine-readable delivery view: one row per canonical task records audit, implementation, learner reachability, QA and deployment evidence, while its progress percentages are derived from those same rows. Before calculating it, the workflow refreshes `origin/main`; a failed refresh downgrades every checkpoint-reachability result instead of trusting a stale remote-tracking ref. A checked backlog box is reported as `backlogChecked` but counts as `canonicalComplete` only after the exact claim has passed post-push verification and the current task definition, pinned proof, checkpoint commit reachable from canonical main, and freshly recomputed nested-evidence manifest all agree. A user-visible task additionally requires a successful `record-release`; `awaiting-release` remains open, incomplete and not deployed. The scheduler uses the same state-aware rule, so pending verification/release does not unblock dependants, and a promoted pending task is not offered for a duplicate claim. Draft, interrupted, expired, replaced, cross-task, stale-definition, branch-only, awaiting-verification, failed-verification and merely self-labelled proof files cannot inflate completion or evidence totals. Route counters are generated from named source registries and carry an explicit claim type so an authored file count cannot be presented as learner reachability. `status` reads this generated ledger rather than calculating a second percentage.

`plan` compiles the canonical checkboxes, dependencies, proof gates, priorities, active claims, lane capacity, and downstream unlock count. It writes resumable work orders, claims, reuse indexes and proof templates beneath an external user-state directory keyed by the repository's physical Git common directory. Every alias and worktree therefore converges on one scheduler state without writing workflow state into candidate-controlled files. `YOMU_ACADEMY_WORKFLOW_STATE` can select an explicitly managed external location for controlled CI or recovery; its physical path is canonicalized before locking.

Authority-bearing configuration lives in a separate governance trust store, by default `~/.config/yomu/academy-production-governance-trust.json`, or at the explicitly managed `YOMU_ACADEMY_GOVERNANCE_TRUST_STORE` path. It must be a current-user-owned, non-group/world-writable regular file outside this repository. The store must expose one unambiguous production approval policy, Fable provider and GitHub policy. Candidate approval configuration may reference only the exact required key IDs; it cannot select a policy or define owners, purpose, validity, public keys, tool binaries, hashes, versions, invocation, repository, workflow or download-host authority.

## Operating rules

1. Work begins only when every canonical dependency is complete.
2. Before authoring, run the slower `index-unreachable` and `index-transcripts` audits, then `salvage TASK`. The task scan inventories every configured recovery document, path-bearing reachable and unreachable commit, branch, surviving worktree (including tracked and untracked changes), stash, reflog entry, and transcript file from the explicit Claude/Codex roots. Every transcript file is read completely and committed by full-file SHA-256; files with the same basename in different roots retain distinct stable identities. A claim re-hashes every transcript and reruns a complete `git fsck --unreachable --no-reflogs --full` object census, including blobs, trees, tags and commits. Size, modification time or a freshness grace window never substitutes for content identity. Candidate ranking ignores generic stopwords, privileges exact task IDs, domain terms and lane-owned paths, and uses `git cherry` to retain patch-equivalent commits in the hashed inventory without proposing duplicate reuse. Every relevant candidate is present in the report and must be explicitly reused or rejected with a reason. Display limits bound only the suggested review queue; omitted display rows remain in the candidate manifest and disposition denominator. Each regeneration records per-source counts, a complete object/transcript manifest hash, the source-snapshot hash and a census hash. Counts are observations, not constants. Regenerated reports carry forward dispositions only when that stable candidate and its evidence hash still match.
3. Code work uses a clean dedicated worktree starting exactly at current `origin/main`. A claim has a random token, fixed worktree, base commit, expiry, renewal and cancellation path. It must reserve its exact planned files up front; changed files outside that reservation cannot pass proof. Reservation identity is physical: the repository and nearest existing parent are resolved with `realpath`, existing and prospective symlink aliases collapse to one key, and any path that resolves outside the repository is rejected. Every work order carries the lane boundary and the external Japanese/Soya roots when relevant.
4. Parallelism is bounded globally and per lane. Status, ledger generation, salvage indexes, claims, proof mutations, promotions, checkpoints, recovery and release recording all share one PID-aware process lock in external state. Physical repository and state aliases collapse through `realpath`, and physical file reservations prevent parallel lanes from touching the same file through aliases. Every materializing transition uses the crash-recoverable journal. Integration remains single-filed.
5. An agent response never closes work. Gate evidence must be a `yomu-academy.gate-attestation/v1` JSON document naming the task, gate, exact HEAD, passing verdict, task owner or allowlisted workflow/CI producer, summary, and hash-bound assertion artifacts. Test commands must be executed by `run-proof`, which records their exit code, transcript and exact Git HEAD. Independent review runs through `run-review`; Node discovers the managed Claude command portably through `PATH`, resolves its canonical realpath, and requires an external trust-store match for executable SHA-256, installation path and reported version before invoking the externally defined Fable policy. Candidate config and environment-selected binary overrides cannot replace that identity. The invocation uses bare/safe mode, no settings sources, no session persistence, an empty strict MCP configuration, disabled slash commands and Chrome, allowlisted read-only tools, and a minimal environment that strips ambient provider/base-URL, cloud, plugin, hook, MCP and settings variables. An explicit `ANTHROPIC_API_KEY` is required. Native model/session/result fields are bound to the prompt, response, task definition and HEAD. Claude Code does not cryptographically attest which remote service answered, so service/provider provenance remains explicitly `unresolved`; the workflow claims only a verified managed invocation and native output shape. Missing, stale or replaced Fable installations fail closed.
6. An `owner` requirement accepts only a `yomu-academy.owner-approval/v3` detached Ed25519 signature whose key and policy are active in the external trust store and whose key ID is referenced by candidate config. The canonical signed payload binds schema, approval revision, trust-store revision, task ID and definition hash, requirement, owner ID, purpose, decision, claim token, HEAD, pre-promotion backlog hash, issue/expiry times, a strong one-use nonce, key ID, algorithm and a hash-bound owner-evidence file. Keys have explicit activation and expiry; revocation is immediate at validation time, and rotation names a later same-owner successor without cycles. The trust store contains public keys only. The repository never generates, requests or stores owner private keys, and fails closed on substitution, replay, expiry, revocation, wrong revision/task/purpose/evidence/key or an unregistered nonce. The owner signs through a separate trusted process.
7. `seal-proof` only operates on a committed, clean slice. It binds the proof to the current task definition, so another task's checkbox may advance without invalidating parallel work. `verify-proof` fetches `origin/main`, checks claim token/worktree/base/HEAD, verifies the exact committed diff against lane ownership, resolves every evidence path physically (rejecting symlink escapes), opens and hashes every evidence file and nested assertion artifact, and rejects stale or fabricated proof. The reuse attestation must be the exact report pinned when the claim was created.
8. `promote --apply` is the only command that checks a canonical item. Canonical state, backlog, index and production-ledger transitions use one durable atomic-write module: a prepared journal records complete before/after images, each target is written by fsync-and-rename, file data is fsynced, and directory fsync is attempted where the platform supports it. Crash injection exists before/after intent, every target write and completion. On restart, untouched transitions roll back and partially applied transitions roll forward. Checkpoint rollback and `reopen` restore both the working-tree backlog and the pre-operation Git index. `recovery-status` remains available even when a file transition or legacy prepared promotion is ambiguous; `recover --rollback` and `recover --roll-forward` provide explicit, evidence-preserving choices without hand-editing private state. Legacy hand-seeded `prepared` lifecycle state is rejected.
9. The integration lock permits exactly one promoted slice per checkpoint. `checkpoint --token` must name the exact promoted claim and rejects expired or superseded claims. It re-hashes the proof, task definition, expected backlog and every nested review/gate/transcript/assertion/approval artifact before gates, after gates, in a retryable checkpoint commit, and before push, so no extra checkbox, mutated proof, stale task or changed nested evidence can ride along. It refuses an advanced `origin/main` instead of rebasing certified commits, runs configured pre-commit gates, pushes, and then enters `awaiting-verification`. Verification independently compares the exact commit through HTTPS `git ls-remote` and the authenticated GitHub API, then requires every workflow and event named by the external GitHub policy to have a successful completed main-branch run for that commit. Candidate commands and self-attested JSON are not release authority. Any verification failure, including unavailable authentication, moves the claim, promotion and checkpoint to `failed-verification`/recoverable, leaves completion open, preserves evidence, and supports `verify-checkpoint --token` retry. User-visible slices move only to `awaiting-release` after these checks pass and remain open, incomplete and not deployed until `record-release` verifies a trusted canonical `gh` installation, HTTPS remote refs, authenticated GitHub release metadata, release-asset bytes, the tagged changelog and the externally configured deployment workflow for the exact tag commit. Only then are the promotion and exact claim `released`.
10. Failed or interrupted work keeps its local claim/proof state and can resume without redoing completed evidence. Expired claims are excluded from status and return to the scheduler after twelve hours; an expired owner cannot renew over a replacement claim. Command evidence has a bounded output size, and `plan`/`prune-state` remove source snapshots no longer referenced by selected or active work, preventing recovery scans from quietly consuming the disk. Test totals are taken from the current runner output; the former static “41 tests” wording is obsolete because lifecycle coverage changes with the contract.

## Why this shape

The critical path is not “generate more files.” It is: establish authoritative denominators and shared contracts, implement dependency-ready vertical slices, verify them in the real product, integrate one slice at a time, and release continuously. The scheduler therefore rewards P0 work, current focus, and tasks that unblock the most descendants while preventing several agents from editing the same lane at once.

Scheduling, salvage, proof commands and ledger generation remain deterministic and model-independent. The one deliberate exception is `run-review`, where Node launches the externally managed Claude Fable policy so the invocation and native output identity can be verified rather than accepted from editable labels. This is not an attestation of Anthropic service provenance.
